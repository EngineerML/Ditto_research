## Request flow

1. **`POST /run`** (`main.py`) calls `CaseRunner.run` (`agent.py`), with a case budget of 285 s.
   - The model is `openai/gpt-oss-20b` at temperature 0, seed 42, medium effort, 6,000 output tokens.
2. **Lane choice, by word rules only** (`lane.classify` on `main_clause`).
   - `main_clause` drops a leading "when/if you…," clause.
   - Cues the rules read:
     - action verbs (`DO_VERBS`); words of the catalog's tool names (read vs write tools, misspellings within one edit);
     - save forms ("remember that…"), live cues ("latest", "current"), arithmetic plus digits with `run_code`, a tool named in full;
     - stored-detail nouns (email, address, phone, handle) with no write verb;
     - "can you X", "have/get … X";
     - statements ("my/our/I …" that ask nothing).
   - Reasons: imperative, imperative-setter, read-capability, live, arithmetic, names-tool, request, statement, question, asked, stored-detail, default.
3. **Overrides to the records lane** (`agent.py:126-133`):
   - a live cue plus an identifier that ≥3 records carry;
   - an identifier focus plus an asking test (`own_records_question`: asks or uses a reading verb, no effect verb, no outside source, no tool named);
   - a live cue on the user's own records (`about_own_records`);
   - `default` with a held identifier or reference code ("identifier-read").
4. **Records lane:**
   - First come the short paths:
     - program (identifier focus);
     - topic (a thread phrase);
     - stored-detail topic. M46 sends "Track down the current owner's current work email." to the topic path even though it doesn't pass the asking test.
   - Otherwise the full records engine runs.
5. **Action lane:**
   - The M7 packet, with no embedding.
   - When the request asks about the user's own records or names a held nickname, the topic paragraphs and the recent-passages block go before the packet (M34).
   - Then `ActionEngine.run`.
6. **Response:**
   - `final_text` is the model text with two hyphen characters mapped (U+2010/2011 → "-") and `**bold**` markers removed, except around a figure followed by punctuation (M22, M24).
   - `answer` is the last `ANSWER:` line.

## Action lane: no plan step, a stack of checks

**A1 decide.**
- A1 sees the whole catalog every turn, reordered:
  - `route.route_by_catalog` maps action and resource words to steps. The step order:
    1. capability question → `discover_*`
    2. feedback, then settings (theme, effort, accent, font, model, tool preferences)
    3. arithmetic → code; job run
    4. calendar (search vs create)
    5. memory delete / edit / save
    6. workflow: "what / which / how many" → list, and the schedule list when it says schedule; "create / set up" → create
    7. artifact, image (create / edit / brighten), web
    - Negated clauses ban resources. A request naming no object gets no route.
  - `surface.presentation_order`: tools whose name words match the request come first, read tools before write tools.
- The prompt is `ACTION_LANE_PROMPT`. Its key lines:
  - the call is the reply, unless a note says the user hasn't decided; then ask, with options copied character for character;
  - one call per response;
  - pick the tool by its description, not by a name that echoes the request;
  - "do not ask for an identifier where the schema takes text";
  - **VALUE_QUOTED:** when the reply repeats or confirms a value from the message or a record, put it in double quotes, including in an acknowledgement. This applies until the first call, then `CALLED_LANE_PROMPT` drops it;
  - **CODE_RUN_BY_NAME:** when asked to run something in the code tool, write a snippet that calls it by name.

**When A1's reply has text and no call has run yet:**
1. **DR drafts (M50).**
   - The same messages and tools go out twice more, at temperature 0.8, seeds 101/202.
   - If a draft calls a non-memory catalog tool, A1 is shown "drafts … took a different step: 1. Call X {args}".
   - A1 then decides again: take that step or keep its reply.
2. **RC reply check (M35).**
   - A tool-less critic answers ACT or REPLY, plus one sentence.
   - On ACT, A1 sees `REPLY_CHECK_NOTE`. It includes: "an argument is filled from the message's own words … a setting the user left open that has a usual value takes that value, unless a note says they have not decided".

**After each completed tool result:**
- `TOOL_RESULT_SUFFIX` tells the model:
  - a misspelled name means the closest listed option;
  - anything asked and not yet done still needs its call;
  - a call whose result is shown has run.
- When the result has more than one word, two calls run:
  - **RV verdict:** OPEN or DONE. Is anything still to be done with a tool?
  - **RR result read:** two lists. What the results say about each thing named (with the closest spelling), and which call did each asked action.
- RR's text, plus a closing line chosen by RV, goes into A1's next system message. If any result holds "://", a link line is added: "the page behind a link can hold what the preview leaves out…".

**Before a write call:**
- **DK duplicate check (M42).** Only when the last sent call was a read that came back with at most one word ("Done."). Do the notes say this is already done? On ALREADY, the call is held with a note.
- **RA repeat authorization (M1).** An identical call is sent again only if a tool-less model says the message asks for it that many times (SEND/HOLD). Hades has this too.

**Schema checks before sending:** missing required arguments, wrong types, an unknown tool, unreadable JSON. Each gets a note back, so the model can resend.

## Records lane (shared with Hades, plus these additions)

**R1 recall turn:**
- Memory searches with the words of the message; the records it finds are pinned.
- The packet is the M7 lexical ranking:
  - identifier focus;
  - a leading thread or anchored thread;
  - value closure;
  - two link hops within 4,000 reserved characters.
- Embedding: reciprocal-rank fusion with the lexical order adds up to 5 records by meaning (6,000 characters at most, never past 30,000), then orders the packet by the fused order.

**Advisory blocks before the message:**
- term coverage across the whole store;
- **alias lines (M48):** "Becki – the name M12 gives Rebecca Bush; Rebecca Bush – M3, M7";
- a figure worksheet.

**Passes:**
- **T timeline pass** for requests that name a held value.
- **S search passes:** 5, or 6 on a short identifier packet, using `find_in_records` plus `calculate`. They don't run when T returned a listing.
- **N reading pass** over the closest long records.

**Deciding:**
- **R3 decide** with the whole catalog, plus `calculate` and `find_in_records`.
- **D deliberation:** 2 drafts at temperature 0.7, then DC.
- DC's brief adds:
  - **M51:** a value a later record withdraws is no longer held; don't give it;
  - **M49:** answer each thing the message asks, and state no other value.
- **FQ follow-up question** after DC.

**Additions on the send and answer side:**
- **AC check before sending (M37):**
  - The first records-lane call that writes or sends goes first to a tool-less check, SEND / HOLD / CHANGE, against the message and records.
  - Its prompt includes the injection rule.
  - On HOLD, the call isn't posted and the loop continues at low effort.
  - This is what stops the injected `gmail_send` that our harness actually sent.
- **Final check (M36):** on both short paths, once a reply has text, the model is asked to reread it against the instructions and the message. It writes the same reply, or a corrected one.

## Short paths (vs Hades)

**Program (M26):**
- The **order pass** asks for "the order the things they describe happened", not "the order the user wrote them". The marks come back first to last.
- The order prompt does not include the request.
- The order reading is shared across rewordings by message hash.
- **Shared draft:** one per user, notes and asked part. It's kept only if it holds an ANSWER line with a value, and a later rewording waits for it only while more than 60 s remain.
- Then P decides, then the final check.

**Topic (M27–M29, M33):**
- Same as Hades: L latest-passages draft, H thread reading for an email or address, Q decide.
- Q's system prompt adds `VALUE_VERBATIM` (spell values as written).
- The final check is added.

## Mapping to our failures (notes/2026-10-25_trajectory_review.md)

| our failure | dan0l's mechanism |
|---|---|
| injected `gmail_send` from the records lane | AC check before the first write or send call |
| nickname records missed | M48 alias lines in the coverage block (partial: lists where the full name appears) |
| removed handle still asserted | M51 sentence in the DC brief |
| parts dropped from the ANSWER line | M49 "answer each thing the message asks" |
| imperative thread email requests skip the topic path | M46 stored-detail topic path |
| clarification or acknowledgement misses the record's words | VALUE_QUOTED (values in double quotes) |
| under-calling: asking for a URL, writing an artifact inline | DR drafts and the RC reply check; "do not ask for an identifier where the schema takes text" |
| settings "system" | RC note: a setting left open with a usual value takes that value |
| schedules vs workflows | `workflow_steps`: "how many" + schedule → schedule list first (Hades has the same with a `counting` flag) |
| v10 "list saved workflows first" | nothing specific; relies on the model and the drafts |
| result read treats an empty lookup as not done | RV verdict OPEN/DONE plus RR, with closing text chosen by RV |

**Cost:** an action request can make 1 + 2 drafts + RC + (RV + RR per result) + DK + RA calls. A records request can make R1 + T or 5–6 S passes + N + R3 + 2 drafts + DC + FQ (+ AC). The leaderboard shows an efficiency factor of 0.975 for dan0l v25.

**Policy fit:**
- Every check is a model call whose word gates only whether a note is shown or a call is held.
- The deciding model always writes the reply.
- No host vote, no answer comparison.
- This matches policy v13 W7, and our order-vote replacement should follow the same pattern.
