## How the official score is built (checked on all five top agents)
- official = mean of 9 samples: the 3 canonical scores (replaced every season by that season's 3 runs) plus the
  6 retained runs of the last 2 seasons. The newest season counts twice (6 of 9), the one before once.
- Everything older is out of the score. Only the champion and the top 5 get new runs at a season boundary;
  a new upload gets its 3 runs at once, on the current season.

## kinfolk: what it asks (released kinfolk v2, submission 69f12191, read in `.cache/miner_gens/dl/`)
- Rotation V6 is a single family, **TwoFavs**: "Which two cheeses does Alexander love[, if you remember? |
  , as far as you know?]". Answer kind list, two gold items, two distractors.
- Item 1 is stated under the asked first name ("Alexander is allergic to mushrooms").
- Item 2 is stated only under a nickname. With `hop2` (on in the shipped build) the binding is two records:
  "...old schoolfriend, Alexander Dunmore, ..." and "Saw the name Sandy Dunmore on the fun run results...",
  then "Sandy had a reaction to coconut again". The item record names neither Alexander nor the predicate.
- Two look-alike nicknames (Sasha, Xander for Alexander) hold the distractor items in the same frame; naming
  either scores 0. 1,000 chatter pairs surround the facts (1,280 pairs per pack).
- So: one item = 0.5, both = 1, a look-alike's item = 0.

## Why our harness gets 0.5
- `memory/aliases.py` accepts an alias only when one record holds both names (`tied`). A two-hop chain
  (Alexander - Dunmore - Sandy) never has one, so the alias pass cannot surface Sandy.
- `asked_names` keeps multi-word capitalized terms only; kinfolk asks about single first names.
- beast, DrPresident and logan show the same 0.5 pattern; dan0l v48 (embargoed until at least 2026-11-11)
  is the only agent that follows the chain.

## beast-d41 released (2026-11-09 22:19 UTC): why it holds up
Release `released/beast-d41-v1_3e59be1e/` (sha256 3c49c680..., 39 files). Its declaration: dan0l v41 plus four
cost changes, every other file byte-identical to v41:
1. the follow-up question is asked inside the reply call (`follow_up_fold`), so the follow-up pass and its
   rewrite turn are not reached;
2. `search_passes` 5 -> 1, `identifier_search_passes` 6 -> 1;
3. `packet_char_budget` 24000 -> 16000;
4. the recall pass is offered the memory tools only, with a one-line system text.

Ours (d42c) is dan0l v42 with the same kind of cuts (no follow-up, 2 passes, 24000 packet, alias pass on asked-name
records, tool offer). v42 over v41 is a few I4 wording changes. Neither has anything for a two-hop nickname.

**The season gap is the self-mask, not the code.** kinfolk's owner coldkey (`...hy43z9ELyx`) is beast's own
(kinfolk v2 5E2J8u7B and beast's hotkey 5CBD7DW3 share it). A column from the scored agent's own owner is
`self_masked`: for beast c0 counts 0 and datagen weighs 0.6 instead of 0.5
(`gate x ((1 - w x |U|) x datagen + w x sum col)`, |U| = 4). Its seed 1 is 0.6 x 0.970 + 0.1 x 3.72 = 0.953;
unmasked it would be 0.910, below dan0l v48 and level with DrPresident. Its datagen (0.958-0.972) and the other
four columns are close to ours. The same owner's kinfolk versions were pinned in seasons 26086-26088 and 26091,
masked for beast each time.

Implication for us: a hard generator pinned under the same coldkey as our agent would be masked for our agent and
count against everyone else. That is generator-side work (ditto-generator), for the user to decide.

## Fix candidate (not built yet)
A deterministic name chain in code, no extra model call: for a person named in the message, find a record
that joins the name to a surname, then records that join another first name to the same surname; pin those
binding records and the records under the other name into the packet, with an advisory note that names the
binding records and leaves the decision to the records. Look-alike nicknames are not in any chain, so the note
never names them. To check before any upload: kinfolk packs (paid, about $0.003 per case) and one datagen
seed for regressions on the official alias and nickname families.

## v12 name chain (d42c, `app/memory/chain.py`, setting `name_chain`, `HARNESS_NAME_CHAIN`)
- For a one-word first name in the message (no surname after it) that stands alone in some record: records that
  write it with a surname, then the surname's other records (at most 4 hold it) that give another first name next
  to it or in a naming sentence ("calls Delia"). The other name must stand alone in some record too, so company and
  place names do not start a chain. Those records and the other name's own records (at most 6) are pinned first in
  the packet, and an advisory note names them by mark: "...the records decide whether Tilly is Matilda".
- No model call, no tool change. The note is an unchecked pointer like the lane's other code-picked notes (I4).
- Offline on kinfolk v2 packs: every chain record pinned in 105/105 cases, no distractor record pinned.
