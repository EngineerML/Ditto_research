## 1. Encounter families

Grading (`grade/encounter.go:34-93`): score = answer credit × required-call coverage × 0.5^forbidden.
- Answer values are matched as bounded tokens. Commas, `$`, `*` and every typographic dash are normalised (`protocol/encounter.go:176-202`).
- LaTeX such as `\$52{,}920` does NOT normalise, so the value is missed.
- A hedge value anywhere in the reply zeroes that value.

### Common mechanics

**Tool menu.** v18 sends 1,484-1,964 tools. In `.cache/v18sets` they split into: 1,130-1,610 snapshot toolkit tools (one free-form `input` argument), 121 workspace first-party extras (groupme/telegram/teamsnap/partner_deal/whatsapp …, about 1,000 schema chars each), 200 connector-pool tools and 33 product tools (about 380 chars each).
- **CROWN** drops the snapshot tools by their schema shape and the 121 extras by a fixed list (`connectors.py:240-255`, called at `agent.py:133`). It then shows pool tools only for apps the message names (`connectors.py:231-234`, `agent.py:136`). Result: the 33 product tools plus the named app's 2-4 tools, the same list on every turn, all product tools always present.
- **OURS** filters only ALL-UPPER toolkit names, then caps the menu at 40 (`connectors.py:85`, `103-156`, `agent.py:118`): `CORE_TOOLS` (20 product + memory) plus the named app's tools, filled by word-overlap rank.
  - The fill is mostly first-party extras and mixed-case snapshot tools (`PLOID_create_monitor`, `teamsnap_*`, `groupme_*`, `telegram_send_message`, `create_partner_deal_blocker`, `get_tool_approvals` …; see any v16 trace "tools listed").
  - Product tools outside `CORE_TOOLS` (`set_theme`, `set_accent_color`, `set_chat_font`, `set_reasoning_effort`, `set_chat_tool_preferences`, `file_feedback_for_team`, add-on tools) are often missing.
  - The model has called the junk entries (`discord_list_connections`, `statuspage_list_components` in practice).

**Request kinds and notes.**
- **CROWN** recognises the five encounter shapes first, reading through one-letter slips (`request_kinds.py:134-160`). If one matches, it returns only that kind (`request_kinds.py:163-166`), "since the single-call notes … would each stop the chain after its first call" (comment at line 134). Each shape has a dedicated note (`guide_tools.py:9-13`), and the note ends with the named app's tools as listed (`guide_tools.py:125-132`). The note goes in the system text and again after the message (`action.py:501-506`).
- **OURS** has no encounter kinds (no match for encounter, incident, pricing or billing in `d42c/app`). Encounter prompts fall into single-call kinds instead:
  - `app_named` → `APP_NOTE` "make that one call now with the {app} tool" (`guide_tools.py:109`, `request_kinds.py:147-148`)
  - `saved_workflow_run`
  - `live_world`: "I need the current …" matches `LIVE_WORLD` at `request_kinds.py:37`. That sets effort to `low` after the first lookup (`action.py:598`), skips RV (`action.py:718`) and adds a note to answer from what the search returns.
  - Our only encounter text is two sentences at `action.py:39` (PROVENANCE row "Action lane prompt").

**Post-result notes (M71).** CROWN has `OPEN_LINK_NOTE`, `WEB_SEARCH_DONE_NOTE`, `UNLINKED_RESULT_NOTE` and `LISTING_APPLY_NOTE` (`action.py:53-59`, `625-633`). After a search on a message that says "page", it tells the model to open the link and not search again. OURS has none of these, so practice traces repeat `search_web` 3-7 times before `read_links`.

**Turns.** CROWN allows 10 action turns (`config.py:37`), OURS 8 (`config.py:36`).

**Polling.** CROWN holds an identical repeat read behind a model check (RA, `tools.py:125-140`). Its question, "how many times does the message ask for this exact call" (`action.py:73-80`), tends to answer HOLD for the second `list_agent_jobs`, so the model must send it again. OURS lets a repeated status read through while its last result says running, pending or retrying (`tools.py:41`, `118`; PROVENANCE row "Multi-step (c)"). **This is one place where OURS is better.** It is a likely cause of CROWN's job 0.78.

**Reply checks.** OURS runs the add-on figure check (AK, `action.py:649-657`) after a named-app read, unless a chain tool was used. On reconcile and handoff (app read only, then a reply or gmail) it can push a one-figure reply. CROWN has no AK.

## 2. Why CROWN is cheaper

Same number of requests, about 2 k fewer prompt tokens each. Estimate for the datagen half, about 1.2 M tokens per run, from practice trace `20261111T002203Z…v15ct_full` (3.96 M prompt for 175 cases):

| our call type (practice, 175 cases) | calls | prompt | CROWN difference | est. saving / run |
|---|---|---|---|---|
| R1 recall | 60 | 0.33 M (5.6 k avg) | CROWN offers only `search_memories` under a short step system (`records.py:253-262`). OURS offers the full listed menu plus the records-lane system text (`records.py:313-321` → `deciding_surface(req.tools)`) | ~0.28 M |
| action turns | 178 | 1.77 M (9.9 k avg) | action packet capped at 12,000 chars (`config.py:30`, `agent.py:223`) vs ours 24,000 (`config.py:29`, `agent.py:166`; practice action packets: median 13.1 k, max 24 k chars); leaner tool list | ~0.25-0.35 M |
| records decide / FC | 163 | 1.51 M (9.3 k) | CROWN answers many memory cases on short evidence views (V, tied-names, SQ; `agent.py:180-208`) from 2-14 notes instead of a 24 k packet; leaner tool list on each call | ~0.3-0.4 M |
| alias pass AN | 34 | 0.08 M | not in CROWN | 0.08 M |
| tool listing on every tool-bearing call | ~400 | — | ours ≈ 4.2 k tokens per call (40 tools, measured: 9.7 k prompt − 5.5 k messages); CROWN ≈ 3.5-3.8 k (33 product + app) | ~0.2-0.3 M |

The slice (175 generator cases) is about 0.5-0.9 M cheaper for CROWN. Most slice cases are alias-list questions (memgen, 5DWjUM, 5D4XN6). CROWN's tied-names view answers them with one call over a few notes. OURS runs R1 (5.6 k), AN (2.4 k) and a deciding call on a 24 k-char packet.

Nothing in CROWN's config caps tokens more tightly than ours apart from `action_packet_chars` 12000. `max_output_tokens`, `long_packet_chars` and `search_passes` are the same.

**To reach ≤ $0.50:** cut ≥ 0.5 M prompt per run. Slim R1 plus the v18 bulk filter plus a 12 k action packet should give about 0.7-1.0 M with no change to model behaviour.

## 3. Memory mechanisms

### CROWN has, OURS lacks
- **Tied-names view** (`evidence.py:287-318`, `person_ties` `:253-284`, `agent.py:183-186`, 208). For a "Name both / What N … does <Full Name> …" question it shows only the notes that write the person's name or a name tied to them, as a whole word. Look-alikes are therefore not shown.
  - The ties are found by called-name cues: first name alone with "goes by", a capitalised word in parentheses, "calls X", or a role another note says the person holds (DECLARATION rows 25b, 28, 30).
  - memgen v6 binds 70 % of nicknames in exactly those forms: first-name, parenthetical, third-party "always calls <First> <Nick>", role-in-between (`.cache/miner_gens/dl/5Hb5Sxe4_01a9c68e/src/gen/v3.go:307-331`).
  - Our alias pass keeps an alias only when one record holds the full asked name and the alias (`memory/aliases.py:40-42`, `70`), so it drops every non-explicit binding. **This most likely explains c0 memgen 0.22 vs 0.87.**
- **Evidence views V** (`evidence.py:93-219`, `view_guide.py`): invoice, quoted project, trip, handle, email-on-date and contact views.
- **Surname chain and name ties woven into the packet** (`records.py:483-495`, `515-519`; `packet.py:346`).
- **Session follow-ups** (`packet.py:464`), **rewritten records** (row 27) and the **case-file event view** (`casefile.py`, row 14b: likely part of v13-open-program 0.954 vs our 0.907).
- **Same-question reuse SQ** (`agent.py:189-207`) and the shared draft SD. These likely explain metamorphic consistency 1.0 vs our 0.833.
- Routed notes for whole-trip, point-in-time and order questions: datagen world-trip-current 1.0 vs 0.89, world-story-quantity 1.0 vs 0.81, absence-* 1.0 vs 0.67.

### OURS has, CROWN lacks
- dan0l v31→v42 base: `READING_RULES`, M85 same-entries reply, M91 alias pass.
- PROVENANCE rows:
  - name chain (`memory/chain.py`, 185 lines)
  - quoted sentences (`chain.said_under`, aliases note)
  - alias pass input restricted to records naming the asked person (`records.py:370-381`)
  - records-lane cost row (no FQ, 2 identifier passes)
  - event-dates program path (`memory/spans.py`, 91 lines)

5DWjUM v5 and 5D4XN6 v6 (ours 0.75/0.73 vs 0.63/0.61) are alias lists whose binding is always explicit and carries the full name ("%s is the one everybody calls %s", `5DWjUMSx_1ba32b5d/src/families/pools.go:121-127`). They also contain a relative's item that writes the target's name ("<Target>'s <relation>, <Relative>, loves X", `families.go:40`, `75`). That fits the following reading, which is a hypothesis and has not been run:
- Our alias pass plus quoted sentences surface exactly the alias's sentences.
- CROWN's view shows every note writing the target's name, including the relative's sentence, which invites an extra wrong item.

reaxgen-b1 v4 (0.56 vs 0.40) has no released source, so it is not analysed here. sn118gen v4 is about even (0.75 vs 0.80). Generator details are another agent's task.

## 4. Recommendation

Score arithmetic (column weight 0.1 each, datagen share 0.5, everything × gate):
- CROWN median 0.812; OURS 0.714.
- The gap is about 0.03 from datagen accuracy, about 0.05-0.06 from the gate (cost factor 0.95-0.97 and metamorphic consistency) and a net of about 0.025 from the columns: memgen −0.065, our +0.04 on c1-c3.

**(a) Rebase on CROWN v228 (recommended).** CROWN is released (available 2026-11-14 03:08 UTC), so building on it with a provenance row is permitted. It already has the encounter notes, the v18 filter, the M71 notes, slim R1, the views, SQ and a cost under $0.50. Port from OURS, in order:
1. **Repeat release for unfinished status reads.** OURS `tools.py:41`, `118-119`: skip RA when the last result of an identical read matches `UNFINISHED_RE`. About 8 lines in CROWN `tools.py:125-134`. Target: job 0.78 → ~1.0. Low risk.
2. **Alias pass plus quoted sentences plus name chain** (`memory/aliases.py` 80, `memory/chain.py` 185, `records.py` hooks at `531-536`, `557`, `574`; config flags). About 300 lines. Wire them into CROWN's records lane only, after `weave_ties`, and only when the tied-names view did not answer. Target: c1, c3 (+0.12 each) and c2 → up to +0.04 composite. Risks: it must not touch memgen (view path first) and adds about 2.4 k tokens per records case with a name (≈ +$0.01-0.02/run; CROWN's run 1 was $0.467).
3. Optional: `memory/spans.py` (event dates on the program path, 91 lines), the `READING_RULES` bullet and the action-prompt sentence at `action.py:39`. `tracked.py` is not needed: CROWN status is already 0.96.

Effort: 1-2 days. Validate first on the free local v18 bench and the 200-seed static atlas. Then do one paid A/B on slice columns c1-c3 plus c0, and the encounter cases only (credit thrift).

**(b) Keep OURS and port from CROWN.** Ports in order of score per line:
1. Encounter kinds and notes. CROWN `request_kinds.py:134-166`, `guide_tools.py:9-13`, `125-137`, about 60 lines. Must return the encounter kind alone so that `APP_NOTE`, `live_world` and AK do not fire.
2. The v18 bulk filter in place of the 40-cap (`connectors.py:236-255`, about 20 lines plus the 121-name list), keeping our offer mechanism.
3. M71 notes (`action.py:53-59`, `625-633`).
4. Slim R1 (`records.py:253-262`).
5. `action_packet_chars` 12000 and `action_max_turns` 10.

Together these are about 150 lines and should close most of the tool-half gap and bring the cost to ≤ $0.50 (gate 1.0 if metamorphic consistency holds). Estimated composite: about 0.77-0.78.
- Closing memgen needs the tied-names view and `person_ties`, which pull in `evidence.py`, `memory/coverage.py` changes (M48), `view_people.py`, `guide_spelling.py` and `english_words.py`: 1,000+ lines written against v30's retrieval. That is high effort and high risk, so (b) caps at about 0.80 unless that is done.
- Metamorphic consistency would still need SQ.

**Verdict: (a).** CROWN is about 0.10 ahead and cheaper. Our advantages are a few small, separable modules (polling release, alias and chain notes) that move onto its records lane cleanly. CROWN's advantages are spread across lanes, retrieval and views. Add a PROVENANCE row naming CROWN v228 (agent `673386d0`), its released archive, and each ported d42c row. Copy no unreleased code.
